# Deployment-prototype de-risker harness `[engineering]`

The third Phase-1 sub-study (see the [Phase 1 overview](index.md)). P1.0.0 built the open-loop harness and P1.0.1
certified its arm-alignment — but both run on the **toy** substrate (STL-10 / synthetic), which Phase 0 showed is a
smoke-test only. This sub-study takes the certified loop onto the **real substrate the exit gate ultimately stands on**
— BDD100K — as a **deployment prototype**: a concrete, from-scratch-runnable system that streams a realistic driving
diet through a config-selected backbone and logs a Phase-0-informed multivariate health signal, so the real-data
ingestion is de-risked before the mode studies (P1.3 / P1.4) need it.

It is deliberately **engineering only**. It is not meant to interpret signals — the acceptance bar is that the pipeline
*runs as intended* and the readings are *sensible* (NaN/finite + plausible-range checks), never that they show a
pathology. The diet's scientific adequacy and every degradation read stay with subsequent studies.

## Motivation

STL-10 is a smoke-test by construction — Phase 0 showed it cannot induce forgetting even under a deliberate control, and
its low-res / few-class regime *amplifies* the benign tunnel-effect rank drop — so reading dynamics off it would be an
artifact at best. The claims rest on BDD's real correlation. The catch is that BDD ingestion (a much larger,
attribute-rich, real image corpus), a *meaningful* learning diet over it, and a health-logging path that survives at
horizon are all unbuilt — and a null on BDD is only interpretable as "no coupling" rather than "underpowered /
mis-configured" if that apparatus has first been proven to run and read sensibly. This sub-study builds and validates
that apparatus.

A second motivation is hand-off. A deployment prototype is a concrete system others can stand up from a *fresh clone*
and run to extract health-signal traces of their own, on their own configurations — so the sub-study is scoped to be
reproducible from scratch, corpus-first (below), and compute-portable.

## Scope of this slice

**In scope.** A new entry point (`scripts/run_deploy_harness.py` + `deploy.yaml`) that adds, over the P1.0.0 harness:

- The **BDD100K substrate** — a new `DataSource` over the BDD100K *images* (not video) with its metadata attributes.
- A **meaningful, configurable diet** over that substrate, with a proposed default (below).
- A **config-selected backbone** (`backbone=mae|je`, one per invocation) and **optional** PC/B5 gate arms.
- **Phase-0-informed multivariate logging** — the full instrument vector each checkpoint, label-free *and*
    labelled-canary channels, every signal tagged with its Phase-0 calibrated status via a code trust-map registry.
- A **two-tier validation** (below) and an explicit **from-scratch setup**.

**Out of scope** (each has its home):

- **Any degradation number or its interpretation** — left to future substudies.
- **The diet's scientific validation** — whether the diet actually *induces* a pathology is a future substudy question;
    P1.0.2 owns the diet *machinery*, not the verdict.
- **FL and the monitor→filter slow edge** — later phases.

## The four deltas vs. the toy smoke

| Delta | P1.0.0 (toy smoke) | P1.0.2 (deployment prototype) |
| -- | -- | -- |
| **Substrate** | STL-10 / synthetic, in-memory | BDD100K images, disk-backed, attribute-rich |
| **Diet** | synthetic `class_blocked` (label blocks) | attribute-driven era ordering over real BDD metadata (configurable; default below) |
| **Backbone** | swept per cell (`C`) | **config-selected** backbone (`mae` or `je`), one per run; PC/B5 gate arms **optional** |
| **Logging** | directional smoke, one instrument set | full multivariate vector, **label-free + canary** channels, **trust-map** annotated |

`backbone=mae|je` runs **one** backbone per invocation rather than co-stepping the two: a co-step at BDD scale can't
materialize the stream and couples two independent deployments precariously, whereas the same config + seed reconstructs
the *same* data regime — so two sequential runs are comparable by construction, no co-step needed. To be precise about
what this leans on: it needs only the **data half** of P1.0.1's certificate — that a rebuilt stream is bit-identical at
fixed seed — not the full in-arm-RNG re-lock decomposition (no two arms are compared step-for-step on the deploy path).
P1.0.1 proved that half on the Phase-0 `EraStream`; `RegimeStream` is a different class, so the same determinism is
*separately* unit-tested for it (`test_is_deterministic_in_seed`, same private-generator isolation). The claim the
deploy path actually depends on — the diet is identical across backbones at fixed seed — holds and is tested directly.

## The diet — configurable machinery, with a proposed default

Where the toy harness mimics correlation with synthetic label blocks, BDD offers real levers: temporal / regime
correlation and attribute shift over its metadata (`weather`, `scene`, `timeofday`). The harness ships the *machinery* —
attribute-driven era ordering — and one default recipe, and leaves the recipe configurable to explore others.

**The default recipe.** Model a driving stream that is (a) *correlated* — eras are regime blocks keyed on
`(timeofday, weather)`, within-era shuffled; (b) *nonstationary* — eras ordered to walk a shift, e.g.
`daytime·clear → daytime·rain → dawn/dusk → night`; (c) *long-tailed* — rare regimes (foggy, snowy, night) stay rare.
Single pass. The correlation-strength knob is the block granularity — the real-attribute analogue of `class_blocked`'s
`block_size`. This is a *default*, not a certified pathology-inducer.

**Three axes to keep straight** (they are easy to conflate):

- **Regime** — a *value* on the ordering axis: a distinct `(timeofday, weather)` combination (e.g. `daytime·clear`,
    `night·rainy`). It is a property of an image, and BDD's val split has **18** of them. Keep this number for the
    *dataset*; the *walk* streams fewer (see the leg caveat below).
- **Era** — a *position in the drive*. The stream sorts the regimes into the shift-walk and streams each as a contiguous
    block; the block delivered at walk-position *n* is era *n*. So "regime" is *what* you order on, "era" is *where you
    are* in that ordering. The distinction matters because the signals are stateful — what you compare across runs is
    "how far into leg *n*", not the absolute regime id (hence `era_index` / `steps_since_transition` in the corpus).
- **Scene** — the **canary** axis: a *different* image attribute (`city street`, `highway`, …), deliberately chosen
    *orthogonal* to the ordering axis. The diet orders on `(timeofday, weather)` but the labelled probe reads `scene`,
    so the canary measures something the stream did **not** sort by.

In short: regime = what you order on, era = where you are in that order, scene = the independent thing you probe.

**18 regimes, 17 legs.** A *leg* is a walk position that actually *delivers* a training block. On BDD's val split the
two numbers differ: the split has **18 regimes**, but one — `dawn/dusk·foggy` — has no training frames left once the
held-out canary probe set is reserved, so it streams no block. The walk therefore delivers **17 legs**. Keep the naming
discipline: **"18 regimes"** whenever you mean the *dataset*, **"17 legs"** whenever you mean the *walk actually
streamed*.

### Warm start — the competent well

A from-scratch backbone is still *settling* when the drive begins, so its early signal motion is the model waking up,
not a response to the stream. Phase 0 removed exactly this confound by reading health only from a **competent well** —
warmed until the loss plateaus (P0.3.10's competence plateau), with the fresh-head transient paid *first* (P0.3.9). The
prototype offers the same discipline. `scripts/warm_well.py` trains the backbone on a **stationary** all-regime sample
(the drive's nonstationarity deliberately withheld) until the SSL loss stops improving, then saves the **whole method**
— encoder *and* head — as a reusable well. Saving the whole method is the load-bearing detail: resuming a warm encoder
onto a *fresh* head would replay the very transient P0.3.9 spent a substudy removing, so a drive that loads the well
(`well=<path>`) starts from genuine competence with none. The well is produced once per backbone and reused across
drives, so every warm drive starts from the identical state and drive-to-drive comparisons carry no per-run warm-up
variance. It is a config pointer, so a **cold** drive (`well=null`, from scratch) is shipped alongside the warm one and
which dynamics only surface each way stays visible. The default warm distribution is a *generally competent* stationary
mix of every regime.

## Logging — the multivariate signal and its trust map

The monitor already emits the full geometry vector at every surface each checkpoint (`rankme`, `mean_feature_var`,
`offdiag_cov`, `uniformity`, `alignment`, `cka_drift`, `cosine_drift`, plus the `_proj` surface for joint-embedding).
P1.0.2 logs all of it, and adds three things:

- **Labelled signals are first-class.** kNN / linear / BWT / FM probes are logged alongside the label-free vector —
    Phase 1 has no deployment label constraint yet, so there is no reason to withhold ground truth. These run on a
    **small, fixed held-out probe set** (`support_per_canary + query_per_canary` images per canary class, reserved once
    at stream construction — e.g. 25 + 25 × 3 scenes = 150 images), *not* on the streamed corpus, which is what keeps a
    reading-every-batch schedule cheap. Per checkpoint the encoder is frozen and run once on the probe set; `knn_acc` is
    a lazy nearest-neighbour lookup, and `linear_acc` *fits a fresh logistic-regression head from scratch* on the
    support features — but on ~75 tiny vectors that converges in milliseconds, so hundreds of checkpoints add up to
    seconds, not minutes. The cost of a drive is the SSL training steps and the one-time image decode, not the probes.
- **Two channels.** The **label-free vector** (what a real deployment would have) and a **labelled canary** (ground
    truth, available because we control the BDD eval set — the very thing P0.5 said MAE quality monitoring requires). To
    avoid leakage, the canary probes an attribute *orthogonal* to the diet's ordering axis (eras blocked on
    `(timeofday, weather)` → canary probes `scene`). Real BDD's scene axis has a long tail — a few classes (`tunnel`,
    `gas stations`) carry only a handful of frames, too few to reserve a balanced held-out probe — so the loader's
    `min_canary_count` knob drops scenes below a frame threshold from the canary (the ordering axis is untouched).
- **A trust map.** Each logged signal carries its Phase-0 calibrated status — `calibrated` / `candidate` / `trap` /
    `needs-two-sided-control` / `needs-labels` — per backbone, so a consumer never fuses a known trap (e.g.
    `uniformity_proj`, calibrated to collapse, *mis-signals* on forgetting). The map is a typed code registry
    (`cafl4ds/health_trust.py`), provenance-pinned to the Phase-0 substudy that earned each verdict, unit-tested for
    completeness against the monitor's emitted menu, and **stamped into the artifact header** so the logged traces are
    self-describing without the code.

The **default signal set** follows the Phase-0 per-(backbone × mode) assignment; any signal can be logged or un-logged
via config, so the pipeline stays flexible.

### The corpus — the hand-off shape

The primary hand-off is a **multivariate time series** anybody mine without the code. Each drive writes a `corpus/` into
its run dir:

- `health.csv` / `health.parquet` — the wide table, **one row per `(seed, arm, checkpoint)`**, every health signal its
    own column. The **`arm`** is which model produced the reading: the deployed backbone is `live`, and *optionally*
    (`gate_arms=true`) two reference arms are co-logged — `pc`, a manufactured-collapse control, and `b5`, a frozen
    init-matched floor. `gate_arms=false` is the **config default** and the hand-off case, so the promoted BDD corpora
    carry the `live` arm only — the column stays first-class so a gate-arm run slots in without a schema change. The
    default is `false` for a second reason too: with the gate arms off, a BDD drive **decodes the corpus once** — the
    one decoded source is threaded through the live arm and (when enabled) the gate arms, cached, rather than re-decoded
    2–3×. Because the signals are *stateful* — a reading integrates the whole history up to that point — each row also
    carries **event-relative coordinates**: the leg it was read in (`era_index` / `era_name`), whether it opens a regime
    **transition** (`is_transition`), and `steps_since_transition`. That is what makes trajectories comparable across
    seeds — you event-lock on the transitions rather than on absolute step. The **seed ensemble** (`seeds=[...]`)
    supplies several trajectories of the same diet; one trajectory is a single draw from a high-dimensional map, the
    ensemble is the dataset. What a seed varies is deliberately *not* the leg ordering: the era walk stays the fixed
    shift-walk (`daytime·clear → … → night·foggy`) for every seed, so the legs line up across the ensemble. A seed
    re-draws two things. (1) The **within-era frame shuffle** — the order of frames inside each regime block (and, if
    `max_train_per_regime` caps a regime, which frames survive; drawn from `RegimeStream`'s own seed-`${seed}`
    generator, isolated from the global RNG per [P1.0.1](P1.0.1.md)). (2) The **model-side RNG** — the from-scratch init
    on a *cold* drive, plus the in-arm augmentation / MAE-masking / dropout draws on *every* drive. What a seed **does
    not** vary is the **held-out canary probe reservation**: which support/query frames each scene sets aside is drawn
    from a separate, *fixed* `canary_seed` (deliberately decoupled from `${seed}`), so every drive in the ensemble — and
    the warm well, which reserves the same way — holds out the *identical* probe set, disjoint from all SSL training.
    That decoupling is load-bearing once the canary is read as ground truth downstream (P1.3 / P1.4): a per-seed
    reservation would leave each warm drive probed on images an earlier drive's well had already shaped unsupervised — a
    soft transductive leak (audit A1). The subtlety on the model side: a *warm* drive resumes the single shared well, so
    its starting weights do **not** vary across seeds — only (1) and the in-arm draws do (a cold drive additionally
    varies its init). Checkpointing is **dense by default** (`eval_every=1`, a reading per batch) for good temporal
    resolution.
- `segments.json` — the **leg map**: the ordered `sunny → rain → …` regime blocks with their step/checkpoint spans, each
    tagged with the label aggregates of the images it streamed (the scene histogram, and — on BDD — the object-category
    histogram from the detection boxes).
- `trust.json` — the per-signal Phase-0 calibrated status.
- `manifest.json` — provenance: schema version, backbone, the seed list, the per-seed Tier-A verdict, git sha.

**What this unlocks.** The paired **(label-free vector, labelled canary)** columns set up *"predict the canary from the
label-free signals"* as a **candidate** downstream multivariate time-series problem this corpus provisions the data for
— *pending a probe-power check* (below): the mapping is only as learnable as the canary's signal-to-noise, and on the
default val diet that margin is thin.

### The canary and its power

The labelled canary is the one channel P1.3 / P1.4 read as ground truth, so its statistical power matters. On the
default BDD **val** diet it is deliberately modest: with the well-populated scenes kept (`min_canary_count=50` → three
scenes, chance ≈ 0.33) and 25 query images each, the probe reads off ~75 images. That is plenty for the *wiring* sanity
check P1.0.2 owns — "canary above chance" confirms the probe is fitted and learning something — but it is a **noisy
target**: the mean sits only a few points over chance and individual checkpoints dip below it. So two things are true
and worth carrying forward, not conflating:

- **For P1.0.2's scope, this is fine.** The canary passing chance is a valid wiring readout; P1.0.2 interprets no
    magnitude.
- **For the downstream affordance, the power must be established first** — flagged to **P1.1** (audit C2). Whether
    "label-free → canary" is learnable above noise is an open question this near-stationary sanity diet cannot answer;
    the mode studies' *real* degradation should move the canary further, which may resolve it — but that must be
    checked, not assumed.

The harness already carries the knobs to make the canary more representative when a study needs it, so this is a
provisioning gap, not a design one:

- **`stream.query_per_canary`** (and `support_per_canary`) — images per scene. Raising the query count directly tightens
    the per-checkpoint estimate.
- **`data.min_canary_count`** — the frame floor a scene must clear to be admitted. *Lowering* it admits more scenes
    (more classes → more diversity, at a lower chance baseline).
- **`data.split=train`** — the real lever for *both* at once. Each retained scene must reserve `support + query` frames,
    and BDD *val* only has ~3 scenes dense enough at count-50; the **train** split (already supported by the loader) has
    the frame density to reserve a larger, multi-scene canary.

## Compute portability

The **core is compute-agnostic**: a single `device` knob (`cpu` / `cuda` / `hpu`) flows through the loop and harness as
today, and the BDD loader yields CPU tensors the loop moves to the device — no hardware branching or `habana` imports in
`cafl4ds/`. Two further levers keep it portable:

- **`img_size` downscales to fit memory.** BDD is natively 1280×720 — far too large to step at any real batch — so the
    loader resizes. This is also the low-memory *portability* lever: downscaling is how a CPU or small-GPU box runs the
    *same* pipeline the Gaudi node runs at full resolution. `img_size` must stay consistent with the backbone's patch
    config (a validated constraint, not a footgun).
- **Hardware stays at the existing edges.** The torch build is selected by the `uv` extra (`--extra cpu` /
    `--extra   cu124`, or the Habana base image for `gaudi`); the only hardware-specific artifacts are
    `docker/gaudi.env.Dockerfile` and `scripts/run_gaudi_dev.sh` (reused unchanged, `-m` mounts `bdd_root`). See
    [developing.md](../../developing.md).

## Methodology — the two-tier validation

P1.0.2 is accepted when both tiers pass. Neither reads a degradation magnitude.

1. **Tier A — the anyone-can-run wiring check.** A fast run on the network-free `data=attr_synthetic` source (or a tiny
    BDD subset) at low resolution and few steps, runnable from a fresh clone with no dataset and no accelerator (a
    plain CPU finishes in seconds). It asserts the pipeline is *wired*: data loads and eras form per the diet; the
    selected backbone steps; **every configured signal is present at every checkpoint** (channel-completeness); both
    the label-free and canary channels populate; the trust map is complete and stamped; nothing goes non-finite; and
    memory stays flat over a short extended run (reusing `all_finite` / `leak_report`). This is the single command that
    answers "is it running as intended?".
1. **Tier B — the sanity-of-readings pass.** The default BDD diet at a sane scale, run on real hardware, confirming the
    readings are *plausible*. This tier is **codified**, not eyeballed: `build_deploy_report` computes a `tier_b` block
    (three criteria — RankMe within `[lo, hi]`, final representation drift `> 0`, and mean canary above chance — with a
    `passed` verdict), stamped into every seed's report beside the Tier-A `validation` block. The thresholds are
    deliberately **loose floors on aggregates**, never a per-checkpoint gate — because the canary is the thin channel:
    its mean clears chance by only a few points and *individual* checkpoints dip *below* chance (see
    [C2](#the-canary-and-its-power)), so a per-step canary gate would flap `passed=false` on a perfectly healthy drive.
    (RankMe stays comfortably in range and the projector drift accumulates fine — the canary is the one that needs the
    aggregate floor.) The floors are config-driven (`tier_b.*` in `deploy.yaml`), so a downstream study can tighten
    them as its diet bites harder. Tier B reads **no degradation magnitude** — the P1.0.0 "harness-validation numbers,
    not claims" bar, on BDD. Kept separate from the Tier-A wiring verdict: a mis-wired pipeline fails Tier A; an
    implausible *reading* on a wired pipeline fails Tier B without touching the wiring gate.

## Setup from scratch

For a fresh clone with nothing else:

1. **Pick the torch build.** `uv sync --group dev --extra cpu` (CPU/CI) or `--extra cu124` (NVIDIA); Gaudi HPUs use the
    Docker image, see [developing.md](../../developing.md).
1. **Get BDD100K.** Download the BDD100K **images** (the 100k-image set — *not* the ~1.8 TB video; the images are
    single-digit GB) and the **legacy labels release** (`bdd100k_labels_images_{train,val}.json`, which carries both
    the per-image `weather` / `scene` / `timeofday` attributes *and* the detection boxes the leg histograms read).
    Arrange them into the canonical layout the loader expects: `images/100k/<split>/*.jpg` and
    `labels/bdd100k_labels_images_<split>.json` (both overridable at the loader). The one real constraint is **RAM, not
    disk** — the loader decodes eagerly, so `img_size` / `max_images` bound the resident footprint.
1. **Point the config at it.** Pass `bdd_root=/abs/path/to/bdd` (an absolute path, mirroring `data_root=/mnt/stl10`; on
    the Gaudi launcher, `-m /abs/path/to/bdd` mounts it at the same path).
1. **Verify, then run.** Run the Tier-A wiring check first (below), then the default diet.

## Artifacts — corpus-first

The **primary deliverable is the config plus the logged-signal corpus** — the health traces from the diet (label-free +
canary channels, the trust map embedded, the leg map with its label aggregates) — not merely a gate verdict. The
pipeline is the *means*: checked in and runnable for other configurations, but the thing a consumer picks up first is
the traces and the exact config that produced them. The corpus is promoted, slimmed, and tracked under
`artifacts/P1.0.2/` following the Phase-0 [promotion policy](../phase0/index.md#artifacts):

- [`synthetic_tierA/`](artifacts/P1.0.2/synthetic_tierA/) — a 3-seed, from-scratch JE run on the network-free synthetic
    substrate, so the corpus format is inspectable without the BDD download. It holds the resolved `config.yaml`, the
    wide `health.csv` (one row per seed × checkpoint — the event-relative coordinates plus the full trust-annotated
    signal vector), the `segments.json` leg map (per-leg scene histograms), `trust.json`, and the `manifest.json`
    provenance. A live run also emits the binary `health.parquet` twin (dropped here — re-run to regenerate).

The **BDD corpora** — the default diet on real BDD100K (val split, `img_size=64`), each a **5-seed ensemble** with a
health reading every batch (`eval_every=1`, ~277 checkpoints/seed over the 17-leg shift-walk), driven on a Gaudi2 HPU.
Each carries the resolved `config.yaml`, the wide `health.csv` (1385 rows), the `segments.json` leg map with per-leg
scene **and** object-category histograms, `trust.json`, and the `manifest.json` provenance (seeds, per-seed Tier-A
verdict, and a `bdd` block: source, image count, regime count, the canary scene set). All three pass Tier B (finite,
RankMe in range, drift accumulates across every seed, canary above chance):

- [`bdd_val_je_warm/`](artifacts/P1.0.2/bdd_val_je_warm/) — the **primary hand-off**: joint-embedding backbone resuming
    the competent well.
- [`bdd_val_je_cold/`](artifacts/P1.0.2/bdd_val_je_cold/) — the same diet from scratch (`well=null`), shipped alongside
    so the warm-vs-cold difference in early dynamics stays visible.
- [`bdd_val_mae_warm/`](artifacts/P1.0.2/bdd_val_mae_warm/) — the masked-autoencoder backbone (warm), exercising the
    config-selected backbone on the real substrate (backbone-surface vector, no `_proj` channel).

The warm/cold pair is shown for the primary (JE) backbone; MAE ships warm only — enough to prove the backbone selector
works on the real substrate. A cold MAE run is one flag away (`backbone=mae`, drop `well=`). The warm wells themselves
(`wells/<backbone>_well.pt`) are produced by `scripts/warm_well.py` (below) and are regenerable, so they are not tracked
— reproducing a warm drive re-warms the well first.

The binary `health.parquet` twin is dropped from each promoted corpus (regenerable — a live run emits it wherever
`pyarrow` is installed; the Gaudi runtime image ships without it, so the drive writes `health.csv` and the parquet is
regenerated on a host that has it).

## How to run

**Tier-A wiring check** — fresh clone, no dataset, no accelerator:

```bash
uv run python scripts/run_deploy_harness.py data=attr_synthetic img_size=32
```

**Tier-B on real BDD** — the workflow that produced the promoted corpora. `data.min_canary_count=50` keeps the canary to
the well-populated scenes (`city street` / `highway` / `residential`); BDD's rare scenes (`tunnel`, `gas stations`,
`parking lot`) have too few frames to support a balanced held-out probe. On the Gaudi node the launcher bind-mounts the
dataset and runs the container `python` (see [developing.md](../../developing.md)); on a CPU/GPU box drop the launcher
and use `uv run python ... device=cpu|cuda`:

```bash
BDD=/abs/path/to/bdd    # canonical layout: images/100k/val/*.jpg + labels/bdd100k_labels_images_val.json
# Shared diet knobs both steps take. The drive adds `gate_arms=false eval_every=1` (keys `warm_well`
# does not define — do not pass them to the warm step).
DIET="data=bdd data.split=val data.min_canary_count=50 bdd_root=$BDD device=hpu img_size=64 \
  stream.support_per_canary=25 stream.query_per_canary=25"

# 1. Warm a reusable competent well once per backbone (encoder + head). The held-out probe set is
#    reserved from a fixed `canary_seed` (default 0), so the well and every drive share it:
./scripts/run_gaudi_dev.sh -m $BDD gaudi-env-cafl4ds:latest 0 \
  python scripts/warm_well.py $DIET backbone=je well_out=wells/bdd_je_well.pt

# 2. Drive the seed ensemble from it. BDD loads eagerly (~0.6 GB), so run each seed as its own
#    invocation (frees memory between seeds) into a per-seed run dir, then merge:
for s in 0 1 2 3 4; do
  ./scripts/run_gaudi_dev.sh -m $BDD gaudi-env-cafl4ds:latest 0 \
    python scripts/run_deploy_harness.py $DIET gate_arms=false eval_every=1 \
    backbone=je well=wells/bdd_je_well.pt seed=$s hydra.run.dir=outputs/bdd_je_warm/s$s
done
```

The cold contrast drops `well=` (from scratch); the MAE backbone swaps `backbone=mae` + its own well. Each drive writes
a `corpus/` (`health.csv` / `health.parquet` where `pyarrow` is present, `segments.json`, `trust.json`, `manifest.json`)
plus the per-seed `reports/` into its Hydra run dir; the per-seed corpora are then unioned into the ensemble
`health.csv` (the seed axis makes the trajectories comparable via the event-relative coordinates). A single in-process
ensemble (`'seeds=[0,1,2,3,4]'`, one invocation) is equivalent on a box with the RAM headroom to hold the diet across
the seed loop. `img_size` / `max_images` bound memory (BDD loads eagerly); `block_size` sets the correlation strength;
`log_signals` prunes the logged signal set.
